# IL-11：哪些测试「声称验证存储语义」，以及那份声称是否成立（2026-11-05）

## 0. 结论先行

| | 值 |
|---|---|
| 仓里测试文件总数（`tests/` + `crates/*/tests/`） | 802 |
| **碰生产存储面**的测试文件 | **124** |
| 其中**既碰生产存储又碰 MemoryStorage**（有歧义的） | **28** |
| 本轮**显式声明**了存储语义的测试 | **28** |
| 碰生产存储但**尚未声明**（候选，工具报告但**不判红**） | **96** |
| `storage_semantics_claims.py check` | **OK**（0 FAIL） |

**28 道声明全部通过**：每一个声明了存储语义的测试，都**真的构造了生产存储**。
反向变异把其中一个改成「只在内存存储上跑」⇒ **立刻判红**（验收口径原话）。

## 1. 为什么需要它

`scripts/gate/check_correctness_tests_production_storage.sh` 的头部写着
「测试是绿的，但它测的不是生产配置」这族问题（#5199 / IAIA-410 F6）。
但那道门禁判的是**服务端**的生产存储装配块（`crates/mysql-server/src/lib.rs` 的
`match storage.as_deref()`），R1–R5 全是分支级的。

IL-11 要补的是另一半：**测试侧**。一个测试若声称自己验证的是**生产存储**语义，
却在关键路径上用内存存储跑 ⇒ 它的断言验证的是内存配置，
生产配置上的同一断言**从未被执行过**。

实测这个风险面不是假想：

| | 数量 |
|---|---|
| 只用生产存储的测试 | 96 |
| **生产存储 + MemoryStorage 混用**的测试 | **28** |

混用的典型例子：`tests/blk2_walstorage_no_escape_hatch_test.rs` ——
它断言的是生产 `WalStorage` / `FileStorage` 上「不得存在逃逸口」，
同时又拿 `MemoryStorage` 当对照组。**这类测试必须显式声明自己在验证什么**，
否则「它到底测的是哪条路径」只能靠读代码猜。

## 2. 口径

### 声明长在测试文件自己身上

```rust
// storage-semantics: ddl-e2e-test
```

放在文件第一行。**声明不放在别的台账里** —— 放在台账里，它就会和代码分家，
改代码不改台账时没人会发现（这正是 IL-6 / C3 那类漂移）。

slug 由文件名推导，所以「这是哪一个测试的声称」不需要人工编。

### 可机器读的清单

`docs/releases/v4.1.0/STORAGE_SEMANTICS_TESTS.jsonl`（28 行，每行一个测试）：
`file` / `slug` / `prod_surfaces` / `mem_surfaces` / `marker`。
由 `storage_semantics_claims.py emit` 从树里的标记生成。

### 三条判据

| 判据 | 内容 |
|---|---|
| **C1** | 声明了存储语义的测试，必须**真的构造生产存储面**（`FileStorage` / `MvccStorage` / `WalStorage` / `FileBackedWalManager` / `ParallelWalStorage`）。不构造 ⇒ 声称是空的 ⇒ 红。 |
| **C2** | 声明了存储语义、却**只**构造内存存储 ⇒ 红（「它的断言验证的不是生产配置」）。 |
| **C3** | 清单与树里的标记必须一致 ⇒ 红（有人改了声明却没重生成清单，或清单里有树里已不存在的声明）。 |

**为什么 C1/C2 拆成两条**：C2 是 C1 的特例（只构造内存 ⇒ 一个生产面都没有）。
拆开是为了让红字直接说出**哪种**失效：「一个生产面都没构造」与
「只构造了内存存储」在修法上不一样。

### 96 个候选**不判红**

工具 `report` 会列出「碰生产存储但还没声明」的 96 个测试，但**不判红**。
理由：一个测试构造了 `FileStorage` **不代表**它声称验证存储语义 ——
很多测试只是拿它当 setup，断言的是 SQL 语义。
把它们直接算进「声称」等于**替作者断言**，那是不诚实的。

⇒ 清单覆盖 124 份里的 28 份，**是本轮的真实覆盖度，不是全部**。
剩余 96 份要靠作者自己声明。

## 3. 反向变异

| 臂 | 做法 | 期望 | 实测 |
|---|---|---|---|
| M1 | 把一个已声明的测试改成**只在内存存储上跑**（`FileStorage` → `MemoryStorage`） | 判红 | rc=1，`C2 … 声称验证存储语义，却只构造内存存储 —— 它的断言验证的不是生产配置` |
| M2 | 删掉一个声明标记 | 判红 | rc=1，`C3 … 在清单里，但树里已经没有 storage-semantics 声明` |
| M3 | 给一个只碰内存存储的文件加声明 | 判红 | rc=1，`C2 … 只构造内存存储` + `C3 … 清单里没有它` |
| 恢复 | 全部还原 | 判绿 | rc=0，`storage_semantics: OK` |

**M1 就是验收口径的原话**（「把某个测试改成只在内存存储上跑 ⇒ 必须红」）。

## 5. 残余风险与未闭环部分

- **清单只覆盖 124 份里的 28 份**（§2 已说明为什么不判红剩下 96 份）。
  清单要长全，得靠作者逐份声明 —— 这是 P1-3 补夹具的副产品。
- **判据是源码级的**（grep 生产存储面 / 内存存储面的符号名）。
  一个测试若**间接**通过某个 helper 走到内存存储，源码上看不出来。
  这类要靠 helper 自己也带标记才能覆盖 —— 本轮没做。
- **C1/C2 不判断「这个测试的断言到底在不在测存储语义」**。
  它只保证「声称了存储语义的测试确实走了生产存储路径」。
  断言本身对不对，是各测试自己的责任。
- **28 份测试只是加了一行注释**，没有改任何测试逻辑；
  改完后本轮**没有重跑这 28 个测试的完整回归** ——
  加注释不影响编译与行为，但严格说没跑过。
- **本条不构成门禁通过声明**：本仓未跑 `ci_gate.sh`。
  归档 run 侧的第二血统复核仍被 IL-9（CI 执行面，runner-03 缺镜像）挡住。
- `check_correctness_tests_production_storage.sh` **本身没改** ——
  IL-11 的扩面由本工具承担（服务端装配块那条门禁继续管服务端那一侧）。
  两侧合起来才覆盖「生产配置被验证过」这个命题。
