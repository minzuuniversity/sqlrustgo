## 2. #5549 —— g13 并发测试

### 2.1 树里的实现（issue 的处方）

commit `de874a8e02` 已经把固定 2 秒窗口换成了**测量派生**的窗口：

```rust
const MIN_WINDOW: Duration = Duration::from_secs(2);
const MAX_WINDOW: Duration = Duration::from_secs(60);
const WINDOW_ITERATIONS: u32 = 3;
...
let window = std::cmp::min(std::cmp::max(MIN_WINDOW, one_iteration * WINDOW_ITERATIONS), MAX_WINDOW);
```

**这一半是对的**，且实测窗口确实随机器变化（本机 `one_iteration` ≈ 350–600ms
⇒ 窗口 ≈ 2–6s）。

### 2.2 但它仍然恒红 —— 残留的「前提」

本机（**load 5–11 / 10 核**，即 issue 说的「有负载的机器」）实测：

```
ALONE: thread A completed 6 heavy queries in 2s
CONTESTED: thread A completed 4 heavy queries in 2s
THROUGHPUT RATIO: contended/alone = 0.667     → 断言红（阈值 0.7）
```

4 次连跑，**每一次都是 6/4 = 0.667** ⇒ 不是噪声。

### 2.3 三组对照实验（定位「谁在拖慢谁」）

| # | 对照线程在做什么 | ratio | 结论 |
|---|---|---|---|
| A | 跑**同一个重查询**（树里代码的实际行为，`Some(HEAVY_SELECT)`） | **0.667 × 4 次** | RED |
| B | 只烧 CPU，**完全不碰数据库** | 0.83 / 1.00 / 1.00 | GREEN |
| C | 跑廉价的 `SELECT 1` | 1.00 / 1.00 / 0.83 | GREEN |

⇒ **不是宿主机 CPU 超订**：对照组 B 同样是「多一个吃满 CPU 的线程」，却几乎不掉。
⇒ 掉的是「第二个**重**查询」本身吃掉的 CPU —— 也就是**比值把「宿主机有没有
空闲核」一起测进去了**。

⇒ 而测试的注释、issue 的描述、断言消息都写着「thread B hammers with
`SELECT 1`」，**唯独代码传的是 `HEAVY_SELECT`**。这个不一致从 #5549 之前
就存在（`git show de874a8e02^` 里同样是 `Some(HEAVY_SELECT)`）。

⇒ **根因**：#5549 换掉了「窗口」这个前提，但比值的**基线**仍然是「无竞争」，
而**竞争臂带着一份 CPU 负载** ⇒ 两者不可比。

### 2.4 本批的修法

**M1 —— 吞吐比值（对宿主机容量归一化）**

启动**两台** ephemeral server，数据相同：
* A = 被测对象；
* B = **对照**。

三臂都用同一个窗口：

| 臂 | 线程 A | 线程 B（对手） | 共享锁？ |
|---|---|---|---|
| ALONE | A 上跑重查询 | 无 | — |
| BASELINE | A 上跑重查询 | **B** 上跑重查询 | **否**（不同 server ⇒ 不同引擎锁） |
| CONTENDED | A 上跑重查询 | **A** 上跑重查询 | **是** |

判据仍是 **`contended >= baseline * 0.7`**（0.7 这个常数**一字未改**，符合 AC3），
但基线换成了「**同样的 CPU 负载、没有共享锁**」的那一臂 ⇒
**宿主机有多少空闲核，在两臂里被同样地扣掉了**，比值因此与宿主机容量无关。
读路径不串行 ⇒ 两臂测到同样的宿主机容量 ⇒ ratio ≈ 1.0；
读路径串行 ⇒ CONTENDED 臂塌到 ≈ 0.5 ⇒ RED。

**M2 —— 探针延迟（直接测「阻塞」这个缺陷本身）**

一个 `SELECT 1` 探针在重查询运行期间被计时：
* `probe_base`：没有重查询时的探针延迟；
* `probe_contended`：重查询正在跑时的探针**最差**延迟。

若重查询持有的是**排他**锁，探针必须等它跑完（数百毫秒）；若走读锁，探针
立即返回。判据 `probe_contended <= probe_base × 10 + 100ms`。
本机实测：`idle=518µs / contended=555µs`（无阻塞），
边界 = `518µs × 10 + 100ms ≈ 105ms` ⇒ 阻塞（≈350ms）会触发 RED。

M2 的采样**必须与重查询重叠**：本批第一版 M2 只采了 30 个样本就结束
（每个 ~0.3ms ⇒ 9ms），**在后台重查询跑完第一次之前就采完了** ⇒
它其实什么都没测到。现已改为：**先等后台重查询至少完成一次，再开始采样**。

**另外**：采样数下限。`N` 个样本时，比值能报告的最小值是
`floor(阈值 × N) / N`；`N = 6` 时是 `floor(0.7×6)/6 = 0.667` —— **低于阈值**
⇒ 真值恰好 0.7 的系统会被报成 0.667 而红，判决取决于落在哪一次迭代上。
故窗口至少保证 `MIN_WINDOW_ITERATIONS = 10` 个样本
（`floor(0.7×10)/10 = 0.7`，阈值恰好可达）。

### 2.5 验收实测

| 判据 | 结果 |
|---|---|
| AC1 `cargo test --all-features --test g13_oltp1_concurrent_select_test` 全绿 | **40 passed / 0 failed**（修复前 39/1） |
| AC2 在**有负载的机器**上重复跑 ≥3 次仍全绿 | **3/3 PASS**（load 5.36/7.26/8.74，ratio 1.11 / 1.29 / 1.29） |
| AC3 吞吐比值判据 `contended >= alone * 0.7` 保持不变 | 阈值常数**未改**；基线由「无竞争」换成「同负载、无共享锁」，是把前提从**假设**换成**测量**，不是放宽 |

### 2.6 判别力（变异自测）

| 变异 | 期望 | 实测 |
|---|---|---|
| 窗口退化为「1 次迭代」 | RED，且消息 = issue 里那句 | RED：`baseline (no contention): thread A only ran 1 queries in 360ms — the heavy query is too slow for the test to be meaningful.` |
| 保留旧实现（对照臂 = 无竞争的 ALONE，且对手跑重查询） | RED（这就是本批修掉的残留） | RED：ratio **0.667**，4/4 次一致 |

**诚实的边界**：本批**没能**构造出一个「server 层的 SELECT 改走 `engine.write()`」
就能让探针被阻塞的变异（该变异下 ratio 仍为 1.00、探针仍不被阻塞）——
说明**今天真正决定读是否串行化的，已经不是 server 层那个
`engine.read()` / `engine.write()` 的选择**（引擎的读路径早已改成 `&self`
的 `execute_read_only`）。M2 因此是一个**只能更严、不会更松**的附加判据：
它观测的是「并发读是否被阻塞」，而阻塞正是缺陷本身。
