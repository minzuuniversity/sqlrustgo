## 1. 口径（三条，全部由 `audit/v4.1.0/board_appendix_check.py` 核对）

| 判据 | 口径 | 为什么是这个口径 |
|---|---|---|
| 看板附录正文 | 附录 A 抽出的正文与仓内源文件（strip 后）**逐字相等** | 旧口径只比「前 200 字」。交接文档一直在长胖，**末尾**追加/删节最常见，而前 200 字口径对末尾改动完全无感 |
| 交接 ISSUE #5599 | 正文**整段包含**仓内源文件（它按设计额外带「发布元数据」段） | 相等会把设计允许的附加段误判为漂移；包含则既挡分叉又放附加段 |
| 附录头三元组 | `文件 N 字节｜注入正文 M 字节（strip 后）｜正文 sha256` 与仓内实测一致 | 两个字节数是**不同口径**（磁盘 vs 注入），混用就是一次口径漂移；sha 让「看起来一样」变成可核对 |

退出码三态：`0` 一致 / `1` 不一致（含附录缺失、字节或哈希漂、ISSUE 分叉）/
`2` 没能核对（API 不可达、源文件不在）。**`2` 绝不是通过。**

## 3. 两条护栏（这次失效暴露出来的，缺一臂就会静默变成摆设）

1. **判据锚点自动定位**：变异臂按关键字在核对器源码里找**整行且唯一命中**的判据行；
   命中 0 次或多于 1 次 ⇒ `exit 3`（源漂了），不再靠写死的字符串。
2. **MUTATION-NOOP 检测**：注入后必须真的改动看板/交接 ISSUE 的字节，
   没改动任何字节 ⇒ 该臂记为 `drift` ⇒ `exit 3`。
   另外要求现场**只触发一条**判据，触发多条说明夹具串味，同样记 `drift`。

## 4. 本次真实失效（写进披露纪律第 9 条）

- 现象：六臂自检前，`m3-byte-metric-drift` 的夹具把附录头的字节数按 `17905` 写死去替换，
  而 39fa9887ff 上交接文件实测 **18818** 字节 ⇒ `replace` 未命中 ⇒ 现场缺陷从未注入 ⇒
  在仓核对器判绿 ⇒ 该臂**形同虚设**。
- 更严重的是：提交信息里写着 `arms=5 discriminating=5`，而在这个提交上重跑只有 4/5。
  原因是**沿用了早先（文件 17905 字时）的读数，没有在该提交上复测**。
- 复现（改动前后各跑一次）：
  ```
  python3 audit/v4.1.0/board_appendix_check_mutations.py     # 现状 6/6
  git stash && git checkout 39fa9887ff -- audit/v4.1.0/board_appendix_check_mutations.py
  python3 audit/v4.1.0/board_appendix_check_mutations.py | tail -1   # 该版只有 4/5，且 m3 显示 NOT-DISC
  ```
- 结论与动作：写死的字节数、写死的句子、写死的 run id 都属于同一类故障（夹具静默脱靶）。
  已改为**从被检对象里读数**＋NOOP 护栏＋锚点自动定位。凡是「计数型」结论，
  **必须在被声称的那个提交上重跑**，不许沿用上一轮的读数。
